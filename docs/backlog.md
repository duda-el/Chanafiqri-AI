## User Story-ები & Acceptance Criteria

### 🔴 Must Have (MVP Scope)

1. **User Story 1: მომხმარებლის ავტორიზაცია, რეგისტრაცია, პაროლის აღდგენა და უსაფრთხოება**
   * **As a** საიტის ვიზიტორს/მომხმარებელს,
   * **I want to** გავიარო რეგისტრაცია/ავტორიზაცია, აღვადგინო პაროლი და მყარად დავიცვა ჩემი ანგარიში,
   * **So that** ჩემი მედია ფაილები და კრედიტების ბალანსი იყოს უსაფრთხოდ დაცული მრავალჯერადი ბოტური რეგისტრაციებისა და არაავტორიზებული წვდომისგან.
   * **Acceptance Criteria:**
     * **Scenario 1: რეგისტრაცია ელ-ფოსტით და ძლიერი პაროლის ვალიდაცია**
       * **Given** ვიზიტორი იმყოფება რეგისტრაციის გვერდზე `/register`,
       * **When** ის შეჰყავს ვალიდური ელ-ფოსტა და ძლიერი პაროლი (მინიმუმ 8 სიმბოლო, ციფრებითა და სიმბოლოებით),
       * **Then** სისტემა აგზავნის 6-ნიშნა ვერიფიკაციის კოდს (OTP) მითითებულ ელ-ფოსტაზე და გადაჰყავს კოდის შეყვანის გვერდზე.
     * **Scenario 2: ელ-ფოსტის ვერიფიკაცია (OTP Code, ვადა და ხელახლა გაგზავნა)**
       * **Given** მომხმარებელმა მიიღო 6-ნიშნა OTP კოდი, რომელსაც აქვს განსაზღვრული ვადა (მაგ. 5 წუთი),
       * **When** ის სწორად შეჰყავს კოდი ან ითხოვს მის ხელახლა გაგზავნას (Cooldown პერიოდით, მაქსიმუმ 3 მცდელობა),
       * **Then** ანგარიში აქტიურდება, იქმნება პროფილი საწყისი კრედიტებით და მომხმარებელი გადადის მთავარ სამუშაო სივრცეში.
     * **Scenario 3: სწრაფი ავტორიზაცია Google-ით (OAuth 2.0)**
       * **Given** მომხმარებელი იმყოფება შესვლის გვერდზე `/login`,
       * **When** ის აჭერს ღილაკს „Continue with Google“ და ადასტურებს თავის Google ანგარიშს,
       * **Then** სისტემა ავტომატურად ქმნის პროფილს (ან შედის არსებულზე) ვერიფიკაციის ნაბიჯის გარეშე.
     * **Scenario 4: არავალიდური მონაცემები და მრავალი ანგარიშით ბოროტად გამოყენებისგან დაცვა (Anti-Abuse)**
       * **Given** მომხმარებელი წერს 8 სიმბოლოზე ნაკლებ პაროლს ან ცდილობს საწყისი უფასო კრედიტების ხელოვნურად მოპოვებას მრავალი დუბლიკატი რეგისტრაციით,
       * **When** სისტემა აფიქსირებს IP ან მოწყობილობის დონეზე საეჭვო აქტივობას/ბოტებს,
       * **Then** სისტემა ბლოკავს მოთხოვნას, ითხოვს Captcha-ს და ეკრანზე გამოაქვს შესაბამისი შეცდომის შეტყობინება.
     * **Scenario 5: Login / Logout და პაროლის აღდგენა**
       * **Given** ავტორიზებული მომხმარებელი იმყოფება სისტემაში ან რაღაცის გამო ვერ შედის (`/forgot-password`),
       * **When** ის ასრულებს Logout-ს ან ითხოვს პაროლის აღდგენის ბმულის გაგზავნას მეილზე,
       * **Then** სისტემა უსაფრთხოდ ასუფთავებს სესიას (JWT/Cookies) ან აგზავნის აღდგენის უნიკალურ ლინკს.

2. **User Story 2: AI ვიდეო და ფოტო გენერაცია (Job Creation, Worker & UI)**
   * **As a** ავტორიზებულ მომხმარებელს,
   * **I want to** გავუგზავნო ტექსტური მითითება (Prompt) ან ატვირთო საწყისი ფოტო/ვიდეო, რომლის დამუშავებაც საიმედოდ წავა რიგში,
   * **So that** მივიღო ახალი ვიზუალური კონტენტი გვერდის დახურვის მიუხედავად და სისტემამ უზრუნველყოს თანმიმდევრული პროცესინგი.
   * **Acceptance Criteria:**
   * **ნაწილი A: Job-ის შექმნა და კრედიტების დაჯავშნა (Frontend & API)**
     * **Given** მომხმარებელი იმყოფება გენერაციის ეკრანზე და აქვს საკმარისი კრედიტები,
     * **When** ის აჭერს „გენერაციას“, სისტემა ქმნის ატომურ ტრანზაქციას: ჯავშნის შესაბამის კრედიტებს, აგენერირებს უნიკალურ `job_id`-ს და აბრუნებს 202 Accepted პასუხს 2 წამში (Idempotency Key-ით, რომელიც იცავს ორმაგი დაჭერისგან).
   * **ნაწილი B: Worker & Provider Adapter (Backend Processing)**
     * **Given** ჯობი ჩაჯდა რიგში (Redis/Celery),
     * **When** Worker-ი იღებს დავალებას და გადასცემს შესაბამის AI პროვაიდერ ინტეგრაციას (Adapter),
     * **Then** მიმდინარეობს მედიის დამუშავება, ტაიმაუტების (Timeout) კონტროლი და API შეცდომის შემთხვევაში კრედიტების ავტომატური დაბრუნება.
   * **ნაწილი C: სტატუსი, გვერდის დახურვა და შედეგის UI**
     * **Given** გენერაციის პროცესი მიმდინარეობს ფონურ რეჟიმში,
     * **When** მომხმარებელი ხურავს ან ტოვებს გვერდს და შემდეგ ბრუნდება (ან უყურებს Live Polling/Websocket სტატუსს),
     * **Then** ინტერფეისი აჩვენებს პროგრესს (Progress Bar) და დასრულებისას გამოსახავს მზა მედიას ჩამოტვირთვის ოფციით.
   * **Scenario 2: გენერაციის მცდელობა ამოწურული ბალანსით (Insufficient Credits)**
     * **Given** მომხმარებლის კრედიტების ბალანსი შეადგენს 0-ს (ან ნაკლებია გენერაციისთვის საჭირო ოდენობაზე),
     * **When** ის აჭერს „გენერაციის“ ღილაკს,
     * **Then** სისტემა არ იწყებს გენერაციის პროცესს, ბლოკავს ღილაკს და გამოსახავს შეტყობინებას: „არ გაქვთ საკმარისი კრედიტები“, შესყიდვის გვერდის (`/checkout`) ლინკთან ერთად.
   * **Scenario 3: გენერაციის შეცდომა (API / Server Error)**
     * **Given** მომხმარებელმა გააგზავნა ვალიდური მოთხოვნა,
     * **When** სერვერზე ან AI API-ზე ხდება ტექნიკური შეცდომა (Failure),
     * **Then** სისტემა აბრუნებს ჩამოჭრილ კრედიტებს უკან მომხმარებლის ბალანსზე და ეკრანზე გამოსახავს შეტყობინებას „გენერაცია ვერ მოხერხდა, სცადეთ თავიდან“.

3. **User Story 3: მზა შაბლონების ბიბლიოთეკა, Face Swap და კონტენტის მოდერაცია**
   * **As a** მომხმარებელს,
   * **I want to** ავირჩიო ტრენდული AI შაბლონი და უსაფრთხოდ გამოვიყენო Face Swap ან ტექსტური გენერაცია,
   * **So that** ჩემმა ატვირთულმა ფოტოებმა და პრომპტებმა გაიარონ ავტომატური მოდერაცია და სისტემამ უზრუნველყოს უსაფრთხო ვიზუალური ტრანსფორმაცია.
   * **Acceptance Criteria:**
     * **Scenario 1: კონტენტის მოდერაცია და Face Swap უსაფრთხოება**
       * **Given** მომხმარებელი ტვირთავს ფოტოს ან აგზავნის პრომპტს Face Swap-ისთვის/გენერაციისთვის,
       * **When** სისტემა ატარებს შიდა AI Content Moderation ფილტრს (არასათანადო, ძალადობრივი ან NSFW კონტენტის ასაცილებლად),
       * **Then** თუ კონტენტი სუფთაა, იწყება Face Swap პროცესი, ხოლო წინააღმდეგ შემთხვევაში სისტემა ბლოკავს მას შესაბამისი გაფრთხილებით.
     * **Scenario 2: არათავსებადი ფოტოს ატვირთვა**
       * **Given** მომხმარებელი ტვირთავს ფოტოს, სადაც სახე არ ჩანს ან ხარისხი ვერ აკმაყოფილებს მოთხოვნებს,
       * **When** ის აჭერს გენერაციას,
       * **Then** სისტემა აფრთხილებს: „ფოტოზე სახე ვერ დაფიქსირდა, გთხოვთ ატვირთოთ სხვა ფოტო“.

4. **User Story 4: გლობალური API ლიმიტების, მომხმარებელთა დაბლოკვისა და კვოტების კონტროლი (Admin Control Panel)**
   * **As a** ადმინისტრატორს,
   * **I want to** ვებ-პანელიდან დავუწესო გლობალური Rate Limit-ები, ვმართო დღიური კვოტები, დავბლოკო დამრღვევი მომხმარებლები და ვკონტროლდე კრედიტების ბალანსი,
   * **So that** ავარიდო სისტემა API პროვაიდერების მხრიდან გადატვირთვას, სპამსა და ფასების მოულოდნელ ზრდას.
   * **Acceptance Criteria:**
     * **Scenario 1: მომხმარებლის კრედიტების მართვა და დაბლოკვა (Ban / Active)**
       * **Given** ადმინი იმყოფება `/admin/users` გვერდზე,
       * **When** ის უცვლის მომხმარებელს კრედიტებს ან აჭერს ღილაკს „Block User“ (არღვევს რა წესებს ან ლიმიტებს),
       * **Then** სისტემა მომენტალურად ანახლებს სტატუსს ბაზაში და უზღუდავს სისტემაში შესვლას/გენერაციას.
     * **Scenario 2: დღიური კვოტებისა და პროვაიდერების Rate Limit-ის მართვა (`/admin/api-limits`)**
       * **Given** ადმინი იმყოფება Control Panel-ის გვერდზე,
       * **When** ის ადგენს თითოეული მომხმარებლის დღიურ კვოტას და AI პროვაიდერების მაქსიმალურ მოთხოვნებს (Throttling),
       * **Then** სისტემა ავტომატურად ანაწილებს მოთხოვნებს რიგში (Queue) და იცავს საიტს API-ის გადატვირთვისგან.

5. **User Story 5: გენერაციის პარამეტრები (Aspect Ratio, Duration, Quality & Settings)**
   * **As a** მომხმარებელს,
   * **I want to** გენერაციამდე ავირჩიო ვიდეოს/ფოტოს ფორმატი, ხანგრძლივობა, ხარისხი და კამერის პარამეტრები,
   * **So that** მიღებული მედია იყოს იდეალურად მორგებული ჩემს მიზნობრივ სოციალურ ქსელზე და კონკრეტულ ამოცანაზე.
   * **Acceptance Criteria:**
     * **Scenario 1: ფორმატისა და რეზოლუციის არჩევა (Aspect Ratio & Resolution)**
       * **Given** მომხმარებელი იმყოფება გენერაციის პარამეტრების პანელში,
       * **When** ის ირჩევს ფორმატს (9:16 Reels/TikTok, 16:9 YouTube, 1:1 Post) და რეზოლუციას (720p, 1080p, 4K),
       * **Then** AI გენერატორი ამზადებს მედიას ზუსტად არჩეული პროპორციებითა და გარჩევადობით.
     * **Scenario 2: ვიდეოს ხანგრძლივობისა და კადრების სიხშირის (FPS) მართვა**
       * **Given** მომხმარებელი აგენერირებს ვიდეოს,
       * **When** ის ირჩევს ხანგრძლივობას (მაგ. 5 წამი, 10 წამი) და FPS-ს (24fps, 30fps, 60fps),
       * **Then** სისტემა ითვლის შესაბამისი კრედიტების ოდენობას ხანგრძლივობის მიხედვით და აგენერირებს მითითებული პარამეტრებით.
     * **Scenario 3: ხარისხის პრესეტები და Render Speed**
       * **Given** მომხმარებელს სურს სწრაფი ან მაღალი ხარისხის შედეგი,
       * **When** ის ირჩევს რეჟიმს: „Fast Draft“ (სწრაფი, დაბალი კრედიტით) ან „Ultra HD / High Quality“ (ნელი, მეტი კრედიტით),
       * **Then** სისტემა გადასცემს შესაბამის ხარისხის პარამეტრებს AI API-ს.

6. **User Story 6: კრედიტების შეძენა (Flitt Payment Gateway)**
   * **As a** მომხმარებელს,

## არაფუნქციური მოთხოვნები (NFR)

- **NFR-01, სისწრაფე (Performance):** ვებ-აპლიკაციის მთავარი გვერდი და გენერაციის სამუშაო სივრცე უნდა იტვირთებოდეს `<= 1.8 წამში`. პროდუქტის წარმადობა და SEO ოპტიმიზაცია მოწმდება **Lighthouse**-ით (Performance Score `>= 90`).
- **NFR-02, დატვირთვა (Load & Concurrency):** სისტემის Backend-მა და Asynchronous Queue (Celery/Redis) არქიტექტურამ უნდა გაძლოს **200 ერთდროულად აქტიურ მომხმარებელს (concurrent clients)**. გენერაციის მოთხოვნების რიგში ჩასმისას შეცდომების მაჩვენებელი უნდა იყოს `0.5%-ზე ნაკლები`. მოწმდება **k6**-ით.
- **NFR-03, API რეაგირების დრო (Latency):** AI პროვაიდერებთან (Higgsfield, OpenAI, Gemini, Claude) მოთხოვნის გაგზავნა და Job Queue-ის შექმნა (API Response: `202 + job_id`) უნდა განხორციელდეს მაქსიმუმ **2 წამში** (გაითვალისწინება რომ ფაქტობრივი პროვაიდერის გენერაციის დრო, მაგ. ფოტო p95 < 60 წმ, ხორციელდება ასინქრონულად). მოწმდება **Postman / Newman** ავტომატიზებული ტესტებით.
- **NFR-04, ხელმისაწვდომობა (Uptime & Availability):** პლატფორმის ხელმისაწვდომობის მაჩვენებელი უნდა იყოს **99.5% (High Availability)**, რაც რეალისტურია მესამე მხარის AI API-ებზე დამოკიდებული სისტემისთვის. სერვერული ხარვეზისას სისტემის დაუგეგმავი გათიშვა არ უნდა აღემატებოდეს მაქსიმუმ **21 წუთს თვეში**. დაკვირვება ხორციელდება **UptimeRobot**-ით.
- **NFR-05, მონაცემთა უსაფრთხოება და ტრანზაქციები (Security & Accuracy):** Flitt-ის გადახდის სისტემასთან ინტეგრაციისას კრედიტების ბალანსის ჩარიცხვა/ჩამოჭრის ცდომილება უნდა იყოს **0%**. მომხმარებლის პაროლები და Auth Token-ები უნდა ინახებოდეს ჰეშირებულად (BCrypt/JWT), ხოლო API Key-ები დაცული იყოს **Environment Secrets** დონეზე.

  მომხმარებელი წარმატებით გადის რეგისტრაციას/ავტორიზაციას (ძალიან მკაცრი ვალიდაციითა და OTP დაცვით), ირჩევს გენერაციის სასურველ პარამეტრებს (ფორმატები, რეზოლუცია, ხანგრძლივობა, ხარისხი), აგენერირებს AI ვიდეოებსა და ფოტოებს ტექსტური პრომპტებით ან იყენებს მზა შაბლონებს და Face Swap-ს (კონტენტის მოდერაციით), ხოლო ადმინისტრატორს კონტროლ პანელიდან შეუძლია გლობალური API ლიმიტების, დღიური კვოტებისა და მომხმარებელთა დაბლოკვა/ბალანსის მართვა.
- **შენიშვნა:** MVP-ის ფარგლებს მიღმა დარჩენილი ფუნქციები (როგორიცაა Flitt-ით გადახდები, მედიის გალერეის სთორჯზე გადატანა/soft delete, Prompt Enhancer და სხვა დამხმარე ოფციები) გადატანილია მომდევნო ეტაპზე (**Should Have**).

  
## Definition of Done (DoD)

User Story ითვლება დასრულებულად (Done), როდესაც:
1. **კოდის ხარისხი:** კოდი გადამოწმებულია გუნდის წევრის მიერ Pull Request-ით.
2. **ტესტირება:** Acceptance Criteria-ები ხელით დატესტილია და ყველა ტესტი წარმატებით გადის.
3. **დიზაინი:** ინტერფეისი გამართულია, პასუხობს Figma მაკეტებს და არის Responsive (მობილურზეც და Desktop-ზეც).
4. **Git Workflow:** კოდი შეერწყა `main` შტოს და **CI (Continuous Integration) ფაიფლაინი წარმატებით გადის**.
5. **უსაფრთხოება:** **კოდში არ იძებნება ჰარდკოდირებული სეკრეტები (Secrets / API Keys)** და ყველაფერი გამოტანილია Environment Variables-ში.
6. **დოკუმენტაცია:** განახლებულია README და საჭიროების შემთხვევაში API ენდპოინტები.
